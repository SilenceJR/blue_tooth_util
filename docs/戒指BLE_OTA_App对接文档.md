## 0. 一页总览

```
┌──────────────┐  ①0x0401(或 PhyPlus AppSvc START_OTA)  ┌──────────────┐
│  应用模式     │ ─────────────────────────────────────▶ │  OTA 模式     │
│ 广播名 BS Ring 2│      设备断链→软复位→进入 OTA 模式      │ 广播名 BS Ring OTA│
│ 服务 0x56FF   │ ◀───────────────────────────────────── │ 服务 5833ff01-…│
└──────────────┘  ⑤REBOOT / 3 min 无连接超时 / 升级完成    └──────────────┘
                                                                │
                            ②连接+MTU+使能 Notify              │
                            ③START_OTA → 逐分区 PARTITION_INFO + 数据流
                            ④OTA_COMPLETE → REBOOT
```

1. App 在**应用模式**下用 `0x0402` 得到 32 位固件版本、产品号和 `boot_flags`，按 §9 判断是否允许升级。
2. App 发 `0x0401`（§3）让设备进入 **OTA 模式**；设备回应后主动断链、复位。
3. App 重新扫描：**MAC = 应用模式 MAC 的最低字节 +1**（mod 256，其余 5 字节不变）、广播名变为 `BS Ring OTA`，连接后走 PhyPlus OTA 协议（§4~§6）把升级包逐分区写入。
4. 全部分区写完收到 `OTA_COMPLETE`，App 发 `REBOOT`，设备重启进入新固件，恢复 `BS Ring 2` 广播。**`OTA_COMPLETE` 只表示传输和烧写完成**；App 必须重连业务模式、用 `0x0402` 读到新版本号后才能显示“升级成功”。
5. 任何时候断电/失败，设备重启后若应用固件校验失败会**自动停留在 OTA 模式**，App 可直接重来（§8）。

## 1. 名词与总体机制

| 名词 | 含义 |
|---|---|
| **应用固件（App FW）** | 戒指日常运行的固件，含计数/显示/蓝牙业务 |
| **OTA Bootloader** | 芯片厂提供的独立小固件，常驻 flash。每次上电先跑它：正常时加载应用固件并跳转；被指令要求或应用固件损坏时停留在 OTA 模式提供升级服务 |
| **应用模式** | 运行应用固件。GATT 上有戒指业务服务 `0x56FF` + PhyPlus **OTA App Service**（§3.2） |
| **OTA 模式** | 运行 OTA Bootloader。GATT 上只有 PhyPlus **OTA Service**（§4） |
| **分区（partition）** | 升级包被切成 ≤ 16 KB 的块，每块带 flash 地址/运行地址/长度/CRC16。设备逐块接收、校验、烧写 |
| **单 bank** | 本芯片 flash 256 KB，只支持单 bank：升级时**原地覆盖**旧应用固件，没有 A/B 回滚；但 Bootloader 本身永不被覆盖，所以失败后总能重新升级 |

固件方保证：
- 进入 OTA 模式前会把未保存的计数记录落盘，App 不需要额外操作。
- OTA 模式下 **MAC = 应用模式 MAC 最低字节 +1（mod 256）**，其余字节不变（固件已实现，待硬件实测）。两种模式 GATT 表完全不同，故意不用同一地址，避免手机按地址缓存 GATT 导致找不到 OTA 服务（PhyPlus 原生 "address plus" / Nordic DFU 同一做法）。App 可用 OTA Service UUID 和名称筛选候选设备，但必须用 Manufacturer Data 中的派生 MAC 确认目标戒指；两种模式的 Manufacturer Data 里各自带的是**本模式**的 MAC。
- OTA 模式 **3 分钟无连接自动软复位**（固件已实现，时长可调）：应用分区未被动过 → 回应用模式；已发过 START_OTA（boot 信息已擦）→ 校验失败自动回到 OTA 模式继续广播，恢复入口不丢（§8）。有连接时不超时，由协议自身的分组超时管理（§6.4）。
- 应用模式下 `0x0401` 在 **电量 < 20 % 且未充电** 或 **芯片未烧 OTA Bootloader** 时拒绝（错误码 `0x05`）。
- **设备端只校验 CRC16，不校验产品号、版本高低和来源**。产品匹配、防降级、包完整性、来源可信由 App 在发送前强制执行（§9）。

## 2. 传输层参数

| 广播名 | `BS Ring 2` | `BS Ring OTA`（已在固件中实现，待实测） |
| 广播 Manufacturer Data | 见现有协议文档 §1.3 | Company ID `0x0504`（空口 `04 05`）+ MAC 6 B（**MSB-first**，与应用模式广播一致）+ 2 B 保留 |
| MAC | 出厂 / 自生成静态地址，例 `C2:11:22:33:44:55` | **应用 MAC 最低字节 +1**，例 `C2:11:22:33:44:56`（`…FF` → `…00`；Bootloader 读同一份 MAC 数据后 +1，已实现，待实测） |
| 广播间隔 | 见现有协议 | 上电后 250 ms；一次连接断开后改为 20 ms 快速广播 |
| 连接间隔（设备期望） | 见现有协议 | 15 ms（min=max=12×1.25 ms），设备会主动发连接参数更新请求 |
| MTU | Android 建议请求 247；Apple 读取系统协商结果 | Android 请求 247；Apple 不主动请求，通过 BLE 传输层读取系统协商后的最大无响应写长度。**设备上限 240**，典型协商结果为 240 → 每包 **237 B**（§6.2）。必须以实际结果为准 |
| 配对/加密 | 不需要 | 不需要 |
| 升级包加密 | — | 当前**明文**（后续若启用 IV/ChipID 加密会另行通知，协议流程不变，只多两条握手命令） |

## 3. 应用模式：触发进入 OTA

两条路任选其一。**推荐 3.1**（走戒指自有协议，一致的帧格式和错误处理）。

### 3.1 戒指协议命令 `0x0402` 查询 OTA 信息 → `0x0401` 进入 OTA 模式（推荐）

先用 `0x0402` 拿到 32 位固件版本、产品号、`boot_flags` 和 Bootloader 版本，完成 §9 的全部判断后再发 `0x0401`。

**`0x0402` OTA 信息查询**：请求 Payload 空；响应 Payload 16 B：

| 偏移 | 字段 | 长度 | 说明 |
|---|---|---|---|
| 0 | fw_version | 4（小端） | `major<<16 \| minor<<8 \| patch`，**与 `.rota` 头里的 `fw_version` 同一编码**；v0.1.0 = `00 01 00 00` |
| 4 | product | 8 | ASCII 补 0，当前 `"Ring2"`；必须与 `.rota` 头的 `product` 完全相等才允许升级 |
| 12 | boot_flags | 1 | 位域，见下表。当前固件返回 `0x01`（仅 bit0） |
| 13 | boot_ver | 3 | Bootloader major/minor/revision（当前 3.1.3）；不在位时全 0。**只用于展示，不得据此推断安全能力** |

`boot_flags` 位定义：

| bit | 含义 | 当前固件 |
|---|---|---|
| 0 | OTA Bootloader 在位（为 0 时 `0x0401` 必然被拒） | 1 |
| 1 | 支持并**要求** AES-CCM 加密固件（MIC 校验），届时 §5 增加三条握手命令且明文包会被拒 | 0 |
| 2 | Bootloader 校验产品号 | 0 |
| 3 | Bootloader 执行最低允许版本检查（设备端防降级） | 0 |
| 4~7 | 保留，必须为 0 | 0 |

内部联调固件返回 `0x01`；量产固件按实际能力返回完整标志（bit1~3 的实现是量产前提，见 §9.3）。App 以 `boot_flags` 为准决定流程，不根据 `boot_ver` 猜测。

**`0x0401` 进入 OTA 模式**：帧格式沿用《BLE 协议》TLV（Head `89 56` … Tail `B5 3A`，CRC16/MODBUS，小端）。

| 项 | 值 |
|---|---|
| CmdType | `0x0401` |
| 请求 Payload | 空（PayLen = 0） |
| 成功响应 Payload | 1 B：`0x01` = 已受理 |
| 错误响应 Payload | `FF 05`（状态错误）：电量 < 20 % 且未充电，或 Bootloader 不在位（`0x0402.boot_flags` bit0 == 0） |

设备行为（固件侧实现）：
1. 回 `0x01` 响应；
2. 约 300 ms 后**主动断开连接**；
3. 链路断开后落盘未保存记录、停马达、关屏，写模式寄存器并软复位进入 OTA 模式（从 `0x01` 到重新广播 `BS Ring OTA` 约 1 s）。

App 行为：收到 `0x01` 后等待断链事件（Android `onConnectionStateChange` / iOS `didDisconnect`），然后进入 §4 扫描。**不要**在收到 `0x01` 后立即主动断开，让设备走自己的断链流程即可；若 5 s 内没有断链，可主动断开并直接扫描 `BS Ring OTA`。

### 3.2 PhyPlus OTA App Service（备用/调试用）

应用固件上同时存在芯片厂标准的 OTA App Service，芯片厂的 `PHYAPP` 调试 App 用它。字节定义如下（可用于用 PHYAPP 先验证链路）。

**GATT**（128-bit UUID，字符串形式）

| 角色 | UUID | 属性 |
|---|---|---|
| Service | `5833ff01-9b8b-5191-6142-22a4536ef123` | — |
| Command | `5833ff02-9b8b-5191-6142-22a4536ef123` | Write |
| Response | `5833ff03-9b8b-5191-6142-22a4536ef123` | Notify（先写 CCCD = `01 00`） |

**命令（写 Command 特征）**

| 命令 | 字节 | 响应（Response Notify） |
|---|---|---|
| INFO | `02` | `00` + MAC 6 B（**LSB-first**，即 `0x0101` 序列号 MAC 和广播 Manufacturer Data 中 MSB-first 顺序的**反序**）+ ASCII `"V3.1.3"`（OTA Bootloader 版本） |
| START_OTA（立即重启） | `01 02` | 无响应；设备直接断链并复位进 OTA 模式 |
| START_OTA（由 App 断链） | `01 02 01` | `00`；之后 **App 主动断开**，设备检测到链路断开后复位进 OTA 模式 |
| 其它 | — | `69`（=105，未知命令） |

`01 02` 中的 `02` 是模式号 `OTA_MODE_OTA`，固定；`03` 为资源升级模式（本项目不用）。

## 4. OTA 模式：GATT 服务

| 角色 | UUID | 属性 | 用途 |
|---|---|---|---|
| Service | `5833ff01-9b8b-5191-6142-22a4536ef123` | — | 与 §3.2 同一个 UUID，但**这是 Bootloader 里的服务，特征多一个 Data** |
| Command | `5833ff02-9b8b-5191-6142-22a4536ef123` | Write（带响应） | 控制命令（§5） |
| Response | `5833ff03-9b8b-5191-6142-22a4536ef123` | Notify | 所有应答（§5.2） |
| Data | `5833ff04-9b8b-5191-6142-22a4536ef123` | **Write Without Response** | 固件数据流（§6） |

### 4.1 OTA 设备识别（身份关联）

OTA 模式与应用模式的 MAC 不同：`OTA_MAC = 应用 MAC，最低字节 +1，按 8 位回绕`（`C2:11:22:33:44:55` → `C2:11:22:33:44:56`；`…FF` → `…00`）。识别分为两步：

1. 用 OTA Service UUID `5833ff01-9b8b-5191-6142-22a4536ef123` 或广播名 `BS Ring OTA` 筛选 OTA 候选设备；服务发现后可用 `5833ff04` Data 特征二次确认 OTA 模式。
2. 解析 OTA Manufacturer Data（Company ID `0x0504` + MAC 6 B MSB-first），仅当其中 MAC 等于目标戒指应用 MAC 的派生值时，才确认是本次升级目标。Android 平台可见地址可用于辅助诊断，但不能替代 Manufacturer Data 身份校验。

Service UUID 和广播名只能说明设备处于戒指 OTA 模式，不能确认它是目标戒指。多枚戒指同时在场时，禁止连接 Manufacturer Data 不匹配的候选设备。

**iOS 不暴露真实蓝牙 MAC**（`CBPeripheral.identifier` 是系统随机 UUID，且两种模式下不保证相同），因此 iOS 不能靠 `deviceId` 或系统地址做身份关联，必须解析 Manufacturer Data。

连接后必须先取得实际 MTU，再写 Response 的 CCCD = `01 00`。Android 请求 MTU 247；Apple 平台由系统协商，App 通过 BLE 传输层读取 `maximumWriteValueLength(.withoutResponse) + 3`。设备只有在收到 CCCD 使能后才把内部状态置为"已连接"，否则所有命令都回状态错误（`64`=100）。

> 判别当前处于哪个模式最稳的方法：服务发现后看 `5833ff04` 特征是否存在（只有 OTA 模式有），或看广播名。

## 5. OTA 模式：控制命令与应答

### 5.1 命令（写 `5833ff02`）

所有多字节整数 **小端**。

| 命令 | 命令码 | 参数 | 总长 | 说明 |
|---|---|---|---|---|
| START_OTA | `0x01` | `sector_num`(1) `burst_size`(1) | 3 | `sector_num` = 本次总分区数（≤ 32）；`burst_size` = 每收到多少个数据包回一次 BLOCK_BURST 应答（§6.3），`0` 按 16 处理，`0xFF` = 不做 burst 应答 |
| PARTITION_INFO | `0x02` | `index`(1) `flash_addr`(4) `run_addr`(4) `size`(4) `checksum`(4) | 18 | 声明第 `index` 个分区（0 起）。四个字段**直接照抄升级包分区表**（§7），`checksum` 低 16 位为 CRC16，高 16 位填 0。设备硬上限 `size ≤ 16 400`（超过回 `06`）；本项目升级包统一切成 `≤ 16 384` |
| REBOOT | `0x04` | 无 | 1 | 立即软复位（无应答） |
| REBOOT（延迟） | `0x04` | `01` | 2 | 应答后置重启标志，**App 断开连接**时设备复位 |
| ERASE | `0x05` | — | — | 仅资源模式可用，本项目**不要发** |
| BLOCK_INFO | `0x03` | — | — | 已废弃，不要发 |
| SEC_CONFIRM / RND_CHANGE / VERIFY_KEY | `0x06/07/08` | 16 B | 17 | 加密固件握手，当前明文模式**不要发** |

### 5.2 应答（`5833ff03` Notify）

三种长度：

| 形式 | 字节 | 含义 |
|---|---|---|
| 正常应答 | `[err][rsp]`（2 B） | `err` 错误码（`00` 成功），`rsp` 应答码 |
| 错误应答 | `[err]`（1 B） | 状态机错误/参数错误，无应答码 |
| 带参数应答 | `[rsp][data…]` | 仅加密握手用 |

应答码：

| rsp | 名称 | 何时出现 |
|---|---|---|
| `0x81` | RSP_START_OTA | START_OTA 处理完 |
| `0x84` | RSP_PARTITION_INFO | PARTITION_INFO 校验通过，可开始发该分区数据 |
| `0x87` | RSP_BLOCK_BURST | 每 `burst_size` 个数据包收齐一次（`err=00`）；或**超时要求重发**（`err=68`=104，§6.4） |
| `0x85` | RSP_PARTITION_COMPLETE | 一个分区数据收齐、CRC 通过、已烧写；还有后续分区 |
| `0x83` | RSP_OTA_COMPLETE | 最后一个分区烧写完成，boot 信息已写入 |
| `0x8A` | RSP_REBOOT | 收到 `04 01` |
| `0x89` | RSP_ERASE | 资源模式 |
| `0xFF` | RSP_ERROR | 未知命令 |

错误码（十进制 → 十六进制）：

| err | 名称 | 含义 / App 处理 |
|---|---|---|
| 0 `00` | SUCCESS | — |
| 5 `05` | NOT_SUPPORTED | 未知命令 |
| 6 `06` | INVALID_PARAM | 分区参数非法（地址越界、size > 16400）→ 升级包有误，终止 |
| 12 `0C` | DATA_ALIGN | 擦除地址/长度未 4 KB 对齐 → 升级包有误 |
| 16 `10` | INVALID_ADDR | 地址非法 → 升级包有误 |
| 23 `17` | SPI_FLASH | flash 写失败 → 从 START_OTA 重来；连续 3 次仍失败则报故障 |
| 100 `64` | OTA_INVALID_STATE | 状态机错误（例如没使能 Notify 就发命令，或顺序错）→ 从 START_OTA 重来 |
| 101 `65` | OTA_DATA_SIZE | 该分区收到的数据超过声明的 size → App 分包错误；修正后从 START_OTA 重来 |
| 102 `66` | OTA_CRC | 分区 CRC 不符 → **从 START_OTA 重来**（不能只重发该分区，见下） |
| 104 `68` | OTA_BAD_DATA | 数据流超时（§6.4）→ 从上次 BLOCK_BURST 确认点重发 |
| 106 `6A` | OTA_CRYPTO | 加密校验失败（明文模式不会出现） |

**恢复规则（以设备源码为准，全文统一）**：
- 只有 `68 87`（数据流超时）是"就地重发"：从上一次 `00 87` 确认的 burst 边界重发，状态机不变。
- **其余任何错误应答**（1 B 错误码，或 `err≠00` 的 2 B 应答）都会把设备状态机打回"已连接"并清空已登记的分区表。App 必须**重新发 START_OTA 并重发全部分区**——因为最终写入 boot 信息时只记录本轮 START_OTA 之后收到的分区，少发任何一个，新固件都无法启动（设备会安全地落回 OTA 模式，但升级失败）。

## 6. OTA 模式：数据流

### 6.1 完整时序

```
App                                              设备
 │── 连接、MTU Request 247 ─────────────────────▶│
 │── 写 5833ff03 CCCD = 01 00 ───────────────────▶│  状态 → CONNECTED
 │── Cmd: 01 <N> <burst> ───────────────────────▶│  擦除 boot 信息扇区
 │◀── Rsp: 00 81 ────────────────────────────────│
 │                                               │
 │  for i in 0..N-1:                             │
 │── Cmd: 02 <i> <flash_addr> <run_addr> <size> <crc> ▶│  校验参数
 │◀── Rsp: 00 84 ────────────────────────────────│
 │── Data: 包1 (MTU-3 字节) ─────────────────────▶│
 │── Data: 包2 ──────────────────────────────────▶│
 │   … 共 burst 个包 …                            │
 │◀── Rsp: 00 87 (BLOCK_BURST) ──────────────────│  收齐一个 burst
 │── Data: … 继续 … 直到该分区 size 字节发完 ─────▶│
 │                                               │  CRC 校验 → 擦除 → 烧写
 │◀── Rsp: 00 85 (PARTITION_COMPLETE)  或  00 83 (最后一个分区: OTA_COMPLETE)
 │                                               │
 │── Cmd: 04 ────────────────────────────────────▶│  软复位 → 加载新固件
 │   (或 04 01 → 收 00 8A → App 断开 → 设备复位)    │
 │                                               │
 │── 重新扫描 BS Ring 2 → 连接 → 0x0402 ──────────▶│
 │◀── fw_version == 升级包 fw_version ────────────│  ← 到这里才算"升级成功"
```

**成功判定**：`00 83`（OTA_COMPLETE）只说明 7 个分区都已收齐、CRC 通过、写入 flash、boot 信息已更新；新固件能否启动要看重启后的结果。App 必须在 REBOOT 后重新扫描 `BS Ring 2`、连接并用 `0x0402` 读到 `fw_version == 升级包 fw_version`，才显示成功；60 s 内没扫到业务模式设备，或扫到的是 `BS Ring OTA`（新固件校验失败，设备回到 OTA 模式），应提示"升级未完成，请重试"并回到 §4 流程。

### 6.2 分包规则（重要）

- 数据写到 `5833ff04`，**Write Without Response**。
- 每包长度 **必须恰好等于 `协商 MTU − 3`**（App 请求 247、设备上限 240 → 协商 240 → **237 B/包**），**只有分区最后一包可以更短**。
  原因：设备按"累计字节数 == 包长 × burst_size"判断一个 burst 结束，包长不足时永远凑不到整倍数，BLOCK_BURST 应答不会出现。
- 设备用 MTU 交换时**它自己接受的值**计算包长（`mtu_a = min(App 请求, 240) − 3`）。若 App 不做 MTU 交换，设备按 20 B/包处理，此时 App 也必须按 20 B 发。
- 本项目升级包每个分区 ≤ 16 384 B（设备硬上限 16 400 B），237 B/包 ≈ 70 包；整个 ~76 KB 固件（7 个分区）≈ 320 包。

### 6.3 流控（平台层 + 协议层两级，两级都要做）

**平台层（始终遵守，与 burst 无关）**
- iOS：每包长度取 `peripheral.maximumWriteValueLength(for: .withoutResponse)`（iOS 11+ 返回 ATT_MTU−3，对本设备为 237）；每次写前检查 `peripheral.canSendWriteWithoutResponse`，为 `false` 时等待 `peripheralIsReady(toSendWriteWithoutResponse:)` 再继续。**不要**照搬"请求 MTU 247"，iOS 不暴露 MTU 请求接口，系统自己协商（结果同样是 240）。
- Android：`requestMtu(247)` 后以 `onMtuChanged` 的值−3 为包长（本设备为 237）；`WRITE_TYPE_NO_RESPONSE` 每次写必须等到 `onCharacteristicWrite` 回调再写下一包，否则会被 GATT 层静默丢包。
- 两个平台都要保证：包长恰好等于上述值（分区最后一包除外），否则 burst 边界永远对不上（§6.2）。

**协议层（burst 应答）**
- `burst_size` 在 START_OTA 里指定。设备每收满 `burst_size` 个整包回一次 `00 87`，App **收到后再发下一个 burst**。
- 建议 `burst_size = 8`；实测吞吐不足再逐步加大。⚠ 固件方实测后会给出推荐值。
- `burst_size = 0xFF`：设备不回 BLOCK_BURST，只靠平台层流控连续发。吞吐最高，但一旦超时（§6.4）要重发整个分区。首版**不要**用。
- 分区末尾不足一个 burst 的部分不会有 `87` 应答，直接等 `85`/`83`。

### 6.4 超时与重传

设备内部两个定时器：
- **包间超时 1 s**：一个 burst 内两包之间超过 1 s；
- **burst 间超时 4 s**：回了 `00 87` 后 4 s 内没收到下一包。

超时后设备发 `68 87`（`err=104, rsp=BLOCK_BURST`），并把接收指针**回退到上次成功应答的 burst 边界**。App 收到 `68 87` 应从该边界重发（即重发当前 burst 的全部包）。若使用 `burst_size = 0xFF`，"上次边界"永远是分区开头，即整个分区重发。App 侧可自行在收到 `68 87` 连续 3 次后放弃并回退到 START_OTA。

App 侧等待建议：等 `87`/`85`/`83` 超时 6 s；等 `81`/`84` 超时 3 s。

### 6.5 CRC16

分区 CRC 由升级包给出，App 不需要自己算。若要校验升级包完整性，算法为：**CRC-16/MODBUS 变体：多项式反射 `0xA001`，初值 `0x0000`**，无最终异或（注意与戒指业务协议帧的初值 `0xFFFF` 不同）。参考实现：

```python
def crc16_ota(data: bytes, seed: int = 0) -> int:
    crc = seed
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc & 0xFFFF
```

## 7. 升级包格式 `*.rota`

固件方随每个固件版本提供一个 `.rota` 文件（由 `Tools/ota_tool.py pack` 从 Keil 输出生成）。App 只需解析头部和分区表，然后按表顺序把数据段发出去。**所有整数小端。**

### 7.1 布局（fmt_ver = 1）

```
偏移    长度  字段
0       4     magic       ASCII "ROTA"
4       2     fmt_ver     格式版本，当前 1
6       1     part_num    分区数 N（1 ≤ N ≤ 32）
7       1     reserved    0
8       4     fw_version  固件版本码 major<<16 | minor<<8 | patch，与 0x0402 的 fw_version 同一编码
12      4     total_size  所有分区数据总字节数 = Σ size_i
16      8     product     ASCII 补 0，当前 "Ring2"；必须与 0x0402 的 product 相等
24      4     reserved    0
28      4     hdr_crc     见 7.2
32      N×16  分区表      每项：flash_addr u32 | run_addr u32 | size u32 | checksum u32(低 16 位 = 该分区数据 CRC16，高 16 位 0)
32+N×16 …     数据区      N 段数据按表顺序紧接，第 i 段长 size_i
```

文件总长必须恰好等于 `32 + N×16 + total_size`。

### 7.2 `hdr_crc` 定义

`hdr_crc = crc16_ota(seed = 0, data = 文件字节 [0, 28) ‖ 分区表 [32, 32+N×16))`，算法即 §6.5（多项式反射 `0xA001`，初值 `0`，无最终异或），结果 16 位放在低 16 位，高 16 位为 0。计算区间**不包含** `hdr_crc` 自身，也不包含数据区。

### 7.3 App 必须拒绝的情况（任何一条命中都不得开始发送）

| 检查 | 条件 |
|---|---|
| 魔数 | `magic != "ROTA"` |
| 格式版本 | `fmt_ver != 1` |
| 分区数 | `part_num == 0` 或 `> 32` |
| 长度 | 文件长 `!= 32 + N×16 + total_size`，或 `total_size != Σ size_i`（截断/多余字节） |
| 头 CRC | `hdr_crc` 不符 |
| 产品 | `product` 与 `0x0402` 返回的 `product` 不相等（按 8 字节比较，含补 0） |
| 版本 | 普通升级要求目标版本更高；同版本仅允许受控恢复重刷；更低版本仅允许服务端按工单授权的受控服务工程包，普通用户入口一律拒绝（详见 §9.2） |
| 分区 size | `size == 0` 或 `> 16 384` 或 `size % 4 != 0` |
| SRAM 分区（`flash_addr < 0x11000000`） | `run_addr < 0x1FFF0000` 或 `run_addr + size > 0x1FFFF400`，或 `flash_addr + size > 0xF000`（bank 60 KB） |
| XIP 分区（`flash_addr >= 0x11000000`） | `flash_addr != run_addr`，或 `flash_addr < 0x11020000`，或 `flash_addr + size > 0x1103D000` |
| 数据 CRC | 某分区数据的 CRC16 与表中 `checksum` 低 16 位不符（App 发送前自行校验一遍） |

### 7.4 发送

PARTITION_INFO 的四个字段**原样**取自分区表；数据段从 `data_offset_i = 32 + N×16 + Σ size_j (j<i)` 起取 `size_i` 字节。分区表已经满足设备的所有约束且顺序有意义（jump table 段必须在主代码段之后），App **不要重排、不要合并**。

实际内容（固件 v0.1.0，`ring_fw_0.1.0.rota`，7 个分区，数据 75 864 B，文件 76 008 B，`hdr_crc = 0x355B`，完整包头见附录 C）：

| # | flash_addr | run_addr | size | checksum | 说明 |
|---|---|---|---|---|---|
| 0 | `0x00000000` | `0x1FFF1838` | 16384 | `0xB9AF` | 应用代码段 1（写到 bank 偏移 0） |
| 1 | `0x00004000` | `0x1FFF5838` | 16384 | `0x06A1` | 应用代码段 2 |
| 2 | `0x00008000` | `0x1FFF9838` | 6000 | `0x942D` | 应用代码段 3 |
| 3 | `0x00009770` | `0x1FFF0000` | 1040 | `0x57E1` | jump table + global config |
| 4 | `0x11020000` | `0x11020000` | 16384 | `0x3C65` | XIP 代码段 1（flash 原地执行，flash_addr == run_addr） |
| 5 | `0x11024000` | `0x11024000` | 16384 | `0xF043` | XIP 代码段 2 |
| 6 | `0x11028000` | `0x11028000` | 3288 | `0x2196` | XIP 代码段 3 |

分区个数和大小随固件版本变化，App 一律以包内分区表为准。

> `flash_addr` 小于 `0x11000000` 的是相对 bank 基址（`0x11011000`）的偏移，设备自己加基址；`flash_addr == run_addr` 且以 `0x11` 开头的是 XIP 段，原地写入。

## 8. 异常与恢复

| 场景 | 设备行为 | App 行为 |
|---|---|---|
| OTA 中蓝牙断开 | 设备状态清零，停留在 OTA 模式广播 | 重连后从 START_OTA 重来 |
| OTA 中戒指断电 / 电量耗尽 | 重新上电时 Bootloader 校验应用固件 CRC 失败 → **自动进入 OTA 模式** | 扫描到 `BS Ring OTA` 从 START_OTA 完整重传 |
| 进入 OTA 模式后 App 放弃（**尚未发 START_OTA**） | 3 min 无连接 → 软复位 → 应用固件完好、校验通过 → 回应用模式 | — |
| 已发 START_OTA / 写入中途断连或 App 放弃 | 3 min 无连接 → 软复位 → boot 信息已擦/分区不全 → 校验失败 → **自动回到 OTA 模式继续广播**（每 3 min 重复一次复位-回 OTA，恢复入口不会丢） | 重连后从 START_OTA 完整重传 |
| 升级完成后重启，但新固件有问题不广播 | 若 CRC 不过会回 OTA 模式；若 CRC 过但固件逻辑异常，需重新进 OTA（无按键情况下只能等 OTA 超时逻辑，⚠ 固件方在评估看门狗兜底） | 提示用户联系售后/重试 |
| App 发错分区参数 | `06`/`10` 错误，状态回到已连接 | 检查升级包，重来 |
| 连续 CRC 错 | `66` | 从 START_OTA 重来（全部重发）；3 次失败则断开重连再试 |

**安全提示**：单 bank 方案在写入期间旧固件已被覆盖，请在 UI 上明确提示用户"升级中请勿远离手机/关闭 App"，并建议电量 ≥ 20 %、最好在充电时进行。

## 9. 版本、产品与来源校验（App 侧强制）

### 9.1 版本编码与映射

| 来源 | 字段 | 编码 | v0.1.0 的值（空口字节） |
|---|---|---|---|
| `0x0402` 响应偏移 0 | fw_version | u32 `major<<16 \| minor<<8 \| patch` | `00 01 00 00` |
| `.rota` 头偏移 8 | fw_version | 同上，**同一编码** | `00 01 00 00` |
| `0x0101` 响应偏移 22 | 固件版本（旧字段，**布局与值均不变**） | u16 `major<<8 \| minor`（不含 patch） | `01 00`（= 0x0001 = "v0.1"，与旧文档一致） |

- `0x0101` 的 52 B 布局和该字段的历史值完全不动，旧 App 不受影响；它只表达 `major.minor`，同一 `major.minor` 下的 patch 升级用它区分不出来。
- **OTA 一律用 `0x0402` 的 32 位值比较**。两者的换算关系：`0x0101 值 == 0x0402 值 >> 8`，可用于自检。

### 9.2 App 必须执行的检查（顺序）

1. `0x0402.boot_flags & 0x01`，否则提示"设备不支持 OTA"；若 bit1 = 1 而 App 只持有明文包，终止并提示需要加密包。
2. `.rota` 通过 §7.3 全部检查。
3. `.rota.product == 0x0402.product`。
4. 版本策略：
   - `.rota.fw_version > 0x0402.fw_version`：正常升级；
   - 相等：允许，作为"恢复重刷"（同版本安全包），需用户在恢复入口明确触发；
   - 更低：**普通用户不得降级**。低版本"服务工程包"只能通过受控签名 + 服务端策略（按设备 MAC/工单授权）下发，App 普通升级入口不得提供；
   - 当前设备端不做版本单调检查（`boot_flags` bit3 = 0），上述规则由 App 强制；Bootloader 最低允许版本检查是量产前提，**实现后 App 侧检查仍保留，两者不互相替代**。
5. 电量 ≥ 20 % 或正在充电（设备端也会检查，但 App 先提示更友好）。

### 9.3 完整性与来源

- 设备端只做 CRC16，**不能证明固件来源可信**；它保证的是"写进去的和 App 发的一致"。
- 来源可信必须在 App 侧闭环：升级包只从固件方/服务器经 HTTPS 下发，服务端对 `.rota` 文件附带签名（建议 Ed25519 或 RSA-2048 over SHA-256 的分离签名），App 验签通过后才解析。签名格式由 App/服务端定，不进本文档。
- 芯片厂方案支持固件加密（AES-CCM，`.hexe`，需要产线烧 efuse key 或 IV）。它的 MIC 是**带密钥**的校验，Bootloader 验 MIC 通过即等价于"固件来自持有密钥的一方"，这是设备端能做到的真实性校验；启用后 §5 会多出 `SEC_CONFIRM/RND_CHANGE/VERIFY_KEY` 三条握手。当前**未启用**，启用时会升级本文档版本并提前通知。
- **当前明确的风险与发布限制**（固件方确认）：Bootloader 不验签名、不验产品/硬件型号、不做版本单调性；链路不配对不加密，任何附近设备都能发 `0x0401` 让戒指进入 OTA 模式并写入任意通过 CRC 的镜像（最坏结果是戒指停在 OTA 模式等待重刷，不会变砖）。因此**开发/内测阶段**可只靠 App 侧校验；**量产版本前**必须完成：① 启用芯片厂加密固件（设备端真实性）；② Bootloader 增加最低版本/产品号检查（固件方排期）；③ App 侧签名验证与 HTTPS 分发。CRC16 在本文档任何地方都不应被理解为安全校验。

### 9.4 分发

升级包命名 `ring_fw_<major>.<minor>.<patch>.rota`；App 只比较 `fw_version` 数值，不解析文件名。

## 10. 联调清单

1. 用芯片厂 `PHYAPP`（固件方提供 apk）先验证：应用模式 INFO → START_OTA → 设备变 `BS Ring OTA` → 选 hex 升级 → 完成后回 `BS Ring 2`。此步验证的是固件链路。
2. 自家 App 实现 §3.1 `0x0402` + `0x0401` → 观察设备断链、重新广播 `BS Ring OTA`，**OTA MAC 符合"应用 MAC 最低字节 +1、8 位回绕"规则**，Manufacturer Data 里的 MAC 同样是 +1 后的值；iOS 端验证仅靠 §4.1 第 1~3 条即可完成关联。
3. 自家 App 实现 §5/§6，用固件方提供的 `.rota` 升级；对照日志核对每条应答。
4. 异常注入：升级到 50 % 时杀掉 App → 重新打开 → 能扫到 OTA 模式设备并完成升级。
5. 异常注入：升级到 50 % 时把戒指拿远断链 → 重连后从头升级成功。
6. 升级后重连业务模式，用 `0x0402.fw_version` 确认等于升级包版本（这是唯一的"成功"判据），`0x0103`/`0x0110` 确认计数与提醒配置未丢失。
7. 异常注入：发完 START_OTA 后立刻断开并等待 > 3 min → 设备应仍以 `BS Ring OTA` 广播（每 3 min 复位一次后回到 OTA 模式）→ 重连后完整重传成功。
8. 异常注入：进入 OTA 模式后不发 START_OTA 等待 > 3 min → 设备回 `BS Ring 2`，原固件与数据完好。
